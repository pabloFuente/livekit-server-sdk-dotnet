# CLAUDE.md

Guidance for AI agents working on this repository. It records the things that are easy to get
wrong; the READMEs ([README.md](README.md), [LivekitApi/README.md](LivekitApi/README.md),
[LivekitRtc/README.md](LivekitRtc/README.md)) hold the user-facing documentation and the
step-by-step developer guides. Keep those READMEs updated when the public API changes.

## What this repo is

Two independent NuGet packages, released separately, in one solution:

| Package | Project | Namespace | Purpose |
| --- | --- | --- | --- |
| `Livekit.Server.Sdk.Dotnet` | `LivekitApi/` | `Livekit.Server.Sdk.Dotnet` | Access tokens, webhooks and Twirp clients for the LiveKit server APIs (Room, Egress, Ingress, SIP, Agent Dispatch, Connector). |
| `Livekit.Rtc.Dotnet` | `LivekitRtc/` | `LiveKit.Rtc` | Real-time participant SDK (join rooms, publish/subscribe media, data, RPC, E2EE) built on the LiveKit Rust SDK through FFI. |

Note the different casing of the two root namespaces (`Livekit.` vs `LiveKit.`). It is
intentional and public; do not "fix" it.

The packages are versioned and released separately: never bump the version of, or add a
changelog entry to, one package for a change in the other.

The official LiveKit SDKs are the reference for behavior and API shape: `livekit/node-sdks`
(`packages/livekit-server-sdk`, `packages/livekit-rtc`) and `livekit/python-sdks` (`livekit-api`,
`livekit-rtc`). When unsure how something should work, check them or https://docs.livekit.io
(a docs MCP server exists at https://docs.livekit.io/mcp) rather than guessing.

`livekit-server-sdk-dotnet.sln` contains only the two libraries and their test projects.
`LivekitApi.Example/` and `LivekitRtc.Example/*` reference the libraries by project path but are
**not** in the solution, so `dotnet build` at the root does not compile them and CI will not catch
a public API change that breaks them. Build them explicitly after changing public signatures.

## Generated code: never hand-edit

- `LivekitApi/proto/*.cs` (including `Twirp.cs`) and `LivekitRtc/Proto/*.g.cs` are generated by
  [generate_proto.sh](generate_proto.sh). They carry an `<auto-generated>` header, CSharpier skips
  them, and the script deletes and recreates them. Any fix goes in the script (it already patches
  namespaces and the Twirp class with `sed`), never in the output. A `PreToolUse` hook
  (`.claude/hooks/guard-generated.sh`) blocks `Edit`/`Write` on these paths, on
  `LivekitRtc/runtimes/` and on both submodules. Edits made through shell commands are not
  intercepted, so the rule applies to you regardless.
- `LivekitApi/proto` is generated from the root `protocol/` submodule (`protocol/protobufs/*.proto`)
  with the namespace rewritten from `LiveKit.Proto` to `Livekit.Server.Sdk.Dotnet`. `Twirp.cs` is
  produced by the `protoc-gen-twirpcs` plugin (`go install github.com/seanpfeifer/twirp-gen/cmd/protoc-gen-twirpcs@v1.1.0`).
- Regenerate with `protoc` 36.2 and `protoc-gen-twirpcs` v1.1.0, the versions that reproduce the
  committed output byte for byte (both sync workflows pin them). v1.1.0 is the plugin's last
  release: its GitHub repository is gone and only the Go module proxy still serves it. Another
  `protoc` can rewrite every generated file of both packages (3.21 reorders the options embedded in
  the serialized descriptors), so move its pin in a change of its own, never inside a sync.
- `LivekitRtc/Proto` is generated from the FFI protos in `LivekitRtc/rust-sdks/livekit-ffi/protocol`
  and keeps the `LiveKit.Proto` namespace. Hand-written code imports it with `using LiveKit.Proto;`
  (`Room.cs` qualifies ambiguous names as `Proto.X`).
- When livekit/protocol adds a `.proto` file, add it to the `protoc` list in `generate_proto.sh`
  (and to the Twirp list if it declares a service). Otherwise it is silently left out.
- Generated code is committed and is what CI builds. The `dotnet.yml` workflow does not check out
  submodules, so nothing may depend on submodule content at build time.
- The `Google.Protobuf` runtime version in `Directory.Packages.props` must be at least as new as
  the `protoc` used to regenerate, or the generated code will not compile.

## Submodules and native binaries

- `protocol/` → https://github.com/livekit/protocol. Used only by `LivekitApi`. Tags look like
  `v1.53.1` (alias `@livekit/protocol@1.53.1`).
- `LivekitRtc/rust-sdks/` → https://github.com/livekit/rust-sdks. Used by `LivekitRtc` for the FFI
  protos. Pinned to a `livekit-ffi/vX.Y.Z` tag. It is configured with `ignore = dirty` because its
  nested submodules (`livekit-protocol/protocol`, `yuv-sys/libyuv`) always show as modified. Do not
  try to "clean" that, and do not commit a changed `rust-sdks` pointer unless you are deliberately
  upgrading it. The nested submodules are only needed to build the FFI from source.
- For both submodules: change the checked-out tag, never their content. Something that seems to
  need an upstream patch is worked around in this repo's own code, or fixed upstream.
- `LivekitRtc/runtimes/<rid>/native/` holds the prebuilt `livekit_ffi` library for win-x64,
  win-arm64, linux-x64, linux-arm64, osx-x64 and osx-arm64. The binaries are **tracked in git**,
  packed into the NuGet package, and the one matching the host RID is copied next to the output
  assembly for local runs (`DllImport("livekit_ffi")` in `Internal/NativeMethods.cs`).
- The binaries come from [LivekitRtc/download_ffi.sh](LivekitRtc/download_ffi.sh)
  (`./download_ffi.sh livekit-ffi/vX.Y.Z` or `./download_ffi.sh X.Y.Z`) and **must match the
  `rust-sdks` tag** that the protos were generated from. Protos and binaries from different FFI
  versions produce runtime failures, not compile errors. Never check in a binary built from an
  uncommitted or unreleased rust-sdks state.
- `download_ffi.sh` checks every `ffi-*.zip` against the SHA-256 digest GitHub recorded for that
  release asset at upload (upstream publishes no checksum file or attestation for them), through
  the GitHub API with `jq`. It writes `runtimes/` only once all six archives have downloaded and
  matched. Every failure (no such release, a missing digest or archive, a failed download, a
  mismatch, a library missing from its archive) exits non-zero and leaves the previous set. A
  mismatch is a reason to stop and investigate, never to bypass the check.
- A binary cannot be reviewed in a diff, so `download_ffi.sh --verify` downloads and checks the
  release of the `livekit-ffi` tag the `rust-sdks` gitlink points to, writes nothing, and exits
  non-zero unless `LivekitRtc/runtimes` holds exactly its six binaries. It is the first step of
  `dotnet.yml` (part of the required `build` check) and runs in `publish.yml` before an `rtc-`
  release is packed. A pull request therefore fails when it changes a binary, moves the submodule
  without the matching binaries, or points it to a commit that is not a `livekit-ffi` release tag.

## Target frameworks and language level

Both libraries target .NET Standard, so most "modern .NET" APIs are unavailable even though the
tests and examples run on `net10.0`.

| Project | TFM | Language | Nullable |
| --- | --- | --- | --- |
| `LivekitApi` | `netstandard2.0` | default for the TFM, i.e. **C# 7.3** | disabled |
| `LivekitRtc` | `netstandard2.1` | `latest` (C# 14 on the .NET 10 SDK) | enabled, `AllowUnsafeBlocks` |
| `*.Tests`, `*.Example` | `net10.0` | default | enabled |

- In `LivekitApi` do not use C# 8+ syntax: no `??=`, `using var`, switch expressions, ranges and
  indices, `is not`, target-typed `new()`, default interface members, async streams, and no `?`
  nullable annotations (`string x = null` is the house style). It depends on `Newtonsoft.Json`,
  `System.IdentityModel.Tokens.Jwt` and `Google.Protobuf`; do not add `System.Text.Json`.
- In `LivekitRtc` the syntax is modern but the BCL is `netstandard2.1`: no `Task.WaitAsync`,
  `ArgumentNullException.ThrowIfNull`, `PeriodicTimer`, `Parallel.ForEachAsync`, non-generic
  `TaskCompletionSource`, `Random.Shared`, `CancellationTokenSource.CancelAsync`, etc.
  `System.Threading.Channels` comes from a NuGet package, not the BCL. `init` accessors (so also
  positional records) and `required` members need compiler polyfills that are not in the project;
  use plain classes with get/set properties.
- Both packages keep `GenerateDocumentationFile` on and the build enforces the XML docs of the
  hand-written code: a missing comment (`CS1591`), a malformed one or an unresolved `cref` is a
  build error, and the documentation rules of `StyleCop.Analyzers` (the only StyleCop category
  enabled; see `.editorconfig` and `stylecop.json`) require a `<summary>`, a `<param>` for every
  parameter, a `<typeparam>` for every type parameter and a `<returns>` on every method that
  returns a value, `Task` included (say what completion means), with every text ending in a
  period. `<inheritdoc/>` satisfies all of it. `.editorconfig` switches the checks off only for
  the generated protobuf files. The comments are what IntelliSense and the published API
  reference show, so write them for the user of the package, not for the maintainer.
- The .NET 10 SDK is required: `global.json` pins it (`rollForward: latestFeature`) and both
  workflows install `10.0.x`. The libraries still target .NET Standard, so the packages keep
  working on older runtimes; only building, testing and the examples need .NET 10.

## Build, format, test

```bash
dotnet build                                   # libraries + tests (not the examples)
dotnet tool restore && dotnet csharpier format . # format; `dotnet csharpier check .` to verify
dotnet test LivekitApi.Tests --filter "Category=Unit"         # no Docker
dotnet test LivekitApi.Tests --filter "Category=Integration"  # Docker
dotnet test LivekitRtc.Tests --filter "FullyQualifiedName~RoomEventsTests"                 # one class
dotnet test LivekitRtc.Tests --filter "FullyQualifiedName~ParticipantEventsTests.ParticipantConnected_Disconnected_EventsFire"  # one test
dotnet test LivekitRtc.Tests --logger "console;verbosity=detailed"   # show ITestOutputHelper output
dotnet pack -c Debug -p:IncludeSymbols=true -p:SymbolPackageFormat=snupkg   # runs package validation
```

Formatting:

- CSharpier is pinned twice: in `.config/dotnet-tools.json` (the tool) and as the `CSharpier.MSBuild`
  package (`Directory.Packages.props`) that `LivekitApi.csproj` references. Keep both at the same
  version, or build-time and hook formatting disagree; Dependabot's `csharpier` group bumps them
  in one pull request. Default settings (no `.csharpierrc`).
  It also formats `.csproj` and `.xml` files, which is why csproj attributes are one per line. Do not
  reflow those by hand.
- `LivekitApi.csproj` references `CSharpier.MSBuild`: a Debug build of that project reformats its
  sources, and a Release build fails on unformatted ones (check mode). `LivekitRtc` has no such
  hook.
- The PR workflow (`dotnet.yml`, Debug) does not enforce formatting. The release workflow
  (`publish.yml`, Release) fails on unformatted `LivekitApi` code through that check mode;
  `LivekitRtc` is never checked. Always format before pushing.
- A `PostToolUse` hook (`.claude/hooks/format-dotnet.sh`) runs CSharpier on every `.cs`/`.csproj`
  file changed with `Edit`/`Write`. Files changed through shell commands are not covered: format
  them yourself.
- `build_local.sh` formats, runs the whole test suite, packs both packages and installs them into
  `~/.private_nuget` with `mono nuget.exe`. It is a release-prep script for the maintainer's
  machine, not a way to "just format".

## API reference (DocFX)

- `dotnet docfx docs/docfx.json --warningsAsErrors && python3 docs/check_api_docs.py` builds the
  API reference of both packages into `docs/_site` and checks what DocFX does not: the server
  sidebar, the `LiveKit.Proto` allow-list and every link between pages. Generated output is
  ignored (`docs/_site`, `docs/obj`, `docs/api-rtc`). `docfx` is pinned in
  `.config/dotnet-tools.json` next to CSharpier.
- The server sidebar is hand-written, `docs/api-server/toc.yml`: the generated one lists the 17
  hand-written types among ~560 protobuf messages. DocFX only uses a sidebar found at the
  physical path the navbar links to, so the server metadata is generated into `docs/obj/api-server`
  and mapped to `api-server/` in `docfx.json`. A new public type of `LivekitApi` needs an entry
  there; the check script fails until it has one.
- `docs/filter.yml` drops `LiveKit.Rtc.Internal`, the protobuf plumbing members of the generated
  messages (`Parser`, `Descriptor`, `MergeFrom`, `WriteTo`, `CalculateSize`, `Clone`, `Equals`,
  `GetHashCode`, `ToString`, field-number constants) and the `*Reflection` holders, and keeps in
  `LiveKit.Proto` only an allow-list of the types the public `LiveKit.Rtc` API uses. When a
  rust-sdks bump makes a public member use another one, the check script names it.
- `globalNamespaceId: Global` gives the global-namespace `Twirp` types that `TwirpException`
  derives from a page, but DocFX links them without the `Global.` prefix, so
  `docs/redirects/*.md` publish redirect pages at those paths. Namespace overviews are overwrite
  files in `docs/namespaces/`; `docs/protobuf-xrefmap.yml` links the Google.Protobuf types to
  protobuf.dev, which publishes no xref map.
- `.github/workflows/docs.yml` publishes `docs/_site` to GitHub Pages
  (https://pablofuente.github.io/livekit-server-sdk-dotnet/) on every push to `main` that touches
  a package or `docs/`, so the site documents the current `main`, not a release.
- `dotnet.yml` also builds the reference on every PR. Both workflows pass `--warningsAsErrors`, so
  a DocFX warning (an xref that does not resolve in `docs/index.md`, `docs/toc.yml` or a sidebar, a
  duplicate tag) fails CI, and run the check script. `docs/docfx.json` passes `NoWarn` for the obsolete-member warnings
  (`CS0612`, `CS0618`) that the metadata build would otherwise report as DocFX warnings.

## Tests

Both test projects are xUnit on `net10.0`. Integration tests start real services with
[Testcontainers](https://testcontainers.com/), so Docker must be running.

**`LivekitApi.Tests`**

- Tests are tagged `[Trait("Category", "Unit")]` or `"Integration"`; tag new ones. xUnit only
  discovers `public` test methods: a non-public `[Fact]` compiles and is silently never run.
- `ServiceClientFixture` (collection `"Integration tests"`) starts redis, `livekit/livekit-server:master`,
  egress, ingress and sip with **fixed container names** (`redis`, `livekit-server`, `egress`,
  `ingress`, `sip`) and **fixed host ports** (6379, 7880). Only one run can be active at a time,
  and containers left over from an interrupted run, or any other deployment using those names (a
  local OpenVidu stack does), make the run fail until removed
  (`docker rm -f redis livekit-server egress ingress sip`, only if they are ours).
- xUnit builds that fixture for every class in the collection, even when
  `--filter "Category=Unit"` selects only the unit tests of such a class. Unit tests therefore go
  in classes without the collection attribute (`ServiceClientUnitTest`, `BaseServiceHttpClientTest`,
  `ConnectorServiceClientTest`, the token and webhook tests), never next to integration tests.
- Unit tests of service clients use `TestHttpMessageHandler` (in `ServiceClientFixture.cs`): it
  records the outgoing request, answers with an empty protobuf, and `LastVideoGrant()` decodes the
  JWT so tests can assert the exact grants a method sends. LiveKit Cloud-only services (Connector)
  cannot be integration-tested and use only this.

**`LivekitRtc.Tests`**

- There are no Category traits. Classes that take `RtcTestFixture` need Docker; the rest
  (`AudioFramePinningTests`, `VideoFramePinningTests`, `VideoFramePlanesTests`,
  `TrackPublishOptionsMappingTests`, `E2EEOptionsMappingTests`, `SdkVersionTests`,
  `DataTrackFrameTests`, `EncodedVideoSourceTests`, `RpcErrorTests`, `FfiClientTest`,
  `AudioCaptureMinimalTest`, `AudioSourcePlayoutTests`, `AudioResamplerTests`) do not.
  `FfiClientTest`, `AudioCaptureMinimalTest`, `AudioSourcePlayoutTests`, `AudioResamplerTests`,
  `EncodedVideoSourceTests` and the two `VideoFrame*Tests` load the native library for the host
  RID; the others are pure managed code.
- `dotnet.yml` tests each of the six shipped binaries on its own platform: every RTC test on
  linux-x64 (`build`) and linux-arm64 (`rtc-linux-arm64`), and on win-x64, win-arm64, osx-x64 and
  osx-arm64 (`rtc-native`) only those seven classes, because hosted Windows and macOS runners
  cannot start Linux containers. A new test class that calls the native library without Docker
  goes in the `--filter` of `rtc-native`.
- `RtcTestFixture` starts, per fixture instance, a private network with redis,
  `livekit/livekit-server:latest`, nginx serving `LivekitRtc.Tests/web/*.html` and
  `selenium/standalone-chrome`. The HTML pages load `livekit-client@latest` from unpkg, so the
  browser tests need internet access. Test classes are spread over several xUnit collections and
  `IClassFixture` usages, so a full run starts several of these stacks; always filter to the class
  or test you are working on.
- `USE_LOCAL_CHROME=true` swaps the Chrome container for a local Chrome and ChromeDriver
  (see [LivekitRtc.Tests/README_LOCAL_CHROME.md](LivekitRtc.Tests/README_LOCAL_CHROME.md)).
- If Testcontainers fails to pull its `ryuk` reaper image, set `TESTCONTAINERS_RYUK_DISABLED=true`;
  the fixtures dispose their containers explicitly anyway.
- Reconnection paths need no network manipulation:
  `Room.SimulateScenarioAsync(Proto.SimulateScenarioKind.SimulateFullReconnect)` forces a full
  reconnect (`Reconnecting`, one `LocalTrackRepublished` per local track, `Reconnected`) and
  `SimulateSignalReconnect` a resume. `RoomEventsTests` and `ParticipantEventsTests` use it.
- A line like `[WARN] RoomEvent.<Name>: ... not found` on the SDK's stderr means the SDK dropped a
  room event. Treat it as a bug signal, not noise. `dotnet test` does not show the test host's
  stderr (neither the console nor the trx logger): set `LIVEKIT_TEST_STDERR_FILE=<path>` and the
  test assembly tees stderr into that file (`LivekitRtc.Tests/SdkStderrCapture.cs`), then grep it
  for `[WARN]` and `[ERROR]`.
- Do not prove E2EE with time-domain audio correlation: Opus transcoding already breaks
  sample alignment, so such a test passes with plaintext media too. Assert something the FFI only
  does with encryption on (`Room.E2EEManager.GetFrameCryptors()`), or compare tone power in the
  frequency domain. `E2EETests` has both accepted styles; `E2EEOptionsMappingTests` only checks
  the `RoomOptions.ToProto()` mapping.
- Images are mutable tags (`master`, `latest`), and so is `livekit-client@latest`; a sudden
  failure may come from an upstream LiveKit change rather than from this repo.

## How the RTC SDK works (read before touching `LivekitRtc`)

- `Internal/NativeMethods.cs` has the P/Invoke surface. `Internal/FfiClient.cs` is a process-wide
  singleton (`FfiClient.Instance`). Every operation is a protobuf `FfiRequest` sent with
  `SendRequest`, which returns an `FfiResponse` synchronously. Asynchronous operations return an
  `AsyncId` in the response and complete later as an `FfiEvent` with the same id, awaited with
  `FfiClient.Instance.WaitForEventAsync(predicate, timeout, token)`. Follow the pattern in
  `Room.ConnectAsync` or `LocalParticipant.PublishTrackAsync` for any new FFI call.
- Events arrive on the native callback thread. `FfiClient` matches waiters first, queues the rest
  (bounded to 1000), then raises `EventReceived`. `Room.OnFfiEvent` filters by room handle and
  `HandleRoomEvent` turns each proto event into a public C# event through `DispatchEvent`, a serial
  FIFO task chain. User handlers run on that chain and their exceptions are logged, not propagated.
  Never block the callback thread, never `await` an FFI event from inside the chain, and never put
  a retry loop in a handler: it delays every following event (that was the 0.1.4 unpublish bug).
  RPC invocations deliberately bypass the chain with `Task.Run`.
- An FFI request's callback and the related room event are independent messages and can arrive
  in either order (for example the `UnpublishTrack` callback and `LocalTrackUnpublished`). Handle
  both orders explicitly instead of assuming one.
- `Room.FfiEventLock` (a `SemaphoreSlim`) guards participant and publication maps. Hold it only to
  mutate state, never across `WaitForEventAsync`.
- Native handles are wrapped in `FfiHandle` (a `SafeHandle`); every `OwnedHandle` the FFI returns
  must be wrapped so it gets dropped. Resource owners (`Room`, tracks, sources, streams, the
  resampler) implement `IDisposable`; `Participant` and `TrackPublication` rely on the
  `SafeHandle` finalizer.
- Managed buffers whose pointer is handed to the FFI (frame capture, frame conversion,
  resampling) must stay pinned until the request has actually been sent, not just while the pointer
  is computed. See `AudioSource.CaptureFrameAsync`, `VideoSource.CaptureFrame`, `VideoFrame` and
  the `*PinningTests`.
- `VideoFrame` describes every planar format through one plane table (`GetPlaneInfosLocal`),
  shared by `GetPlane` and by the buffer info sent to the FFI. A new `VideoBufferType` goes in
  that table plus a case in `VideoFramePlanesTests`; do not special-case formats elsewhere.
- An FFI panic terminates the process (`Environment.Exit(1)` in `FfiClient`) by design.
- Logging is plain `Console` / `Console.Error` with `[WARN]`/`[ERROR]` prefixes; there is no
  `ILogger`. Keep that style.
- Public option classes (`RoomOptions`, `TrackPublishOptions`, `E2EEOptions`, ...) map to protos
  via `ToProto()`. New options are nullable and only assigned when set, so the FFI defaults apply
  when unset. `TrackPublishOptionsMappingTests` iterates the proto descriptor and fails when a
  regenerated `Proto.TrackPublishOptions` has a field the SDK does not expose; after a rust-sdks
  bump, fix that by exposing the field, not by weakening the test. E2EE settings go in the
  `Encryption` proto field (`E2Ee` is deprecated).
- Design goal: feature parity with the server-side RTC SDKs for Node
  (`livekit/node-sdks`, `packages/livekit-rtc`) and Python (`livekit/python-sdks`, `livekit-rtc`),
  which wrap the same FFI. When adding or fixing behavior, check how those two do it.

## Conventions in the API SDK

- One `XServiceClient : BaseService` per Twirp service. Each method builds the minimal JWT grants
  for that RPC with `AuthHeader(new VideoGrants { ... })` (plus `SIPGrants` for SIP) and calls
  `SendAsync("twirp/livekit.<Service>/<Method>", request, <Response>.Parser, token)` from
  `BaseService`, which builds one `HttpRequestMessage` per call (host, bearer token, user agent)
  and raises `TwirpException` on errors. The clients do not call the generated `Twirp` class; it
  stays in the package for external callers. Routes are copied from `Twirp.cs`, and
  `api_coverage.py` matches those literals. Never write the token to
  `httpClient.DefaultRequestHeaders` (concurrent calls would swap tokens). Which grant
  each RPC needs is copied, never invented, from the reference SDKs (`livekit/node-sdks`
  `packages/livekit-server-sdk`, `livekit/python-sdks` `livekit-api`, `livekit/server-sdk-go`).
- Request and response types are the generated protobuf messages; do not wrap them in custom DTOs.
- The public surface is checked by package validation against the last released version
  (`PackageValidationBaselineVersion`). `dotnet pack` fails on any break that
  `CompatibilitySuppressions.xml` does not list, locally and in CI: `dotnet.yml` packs on every
  pull request, so the required `build` check catches it. Never change or remove a public signature in
  hand-written code: add an overload instead. The only acceptable breaks are the ones forced by
  `livekit/protocol` (see the upgrade section).
- Every client accepts an optional `HttpClient`, which the SDK never modifies (it may be shared or
  already in use): the host, token and User-Agent go on each request. Twirp routes are relative
  (`twirp/livekit.X/Y`) and `BaseService` appends the trailing `/` to the host before resolving
  them; that is what makes base-URL subpaths (`https://host/livekit`) work. `apiKey`/`apiSecret`
  fall back to `LIVEKIT_API_KEY`/`LIVEKIT_API_SECRET` when omitted, as do `AccessToken`,
  `TokenVerifier` and `WebhookReceiver`.
- A new client method needs: a unit test asserting route and grants, an integration test when the
  service runs locally, a section in `LivekitApi/README.md` (the changelog links to it), and a
  changelog entry.

## Upgrading livekit/protocol (API SDK)

1. `cd protocol && git fetch --all && git checkout vX.Y.Z && cd ..`, commit as
   `Update livekit/protocol to vX.Y.Z`.
2. `./generate_proto.sh`, commit as `Regenerate proto C# files`. The script deletes
   `LivekitApi/proto` before it checks for `protoc` and `protoc-gen-twirpcs`; if it fails,
   `git checkout -- LivekitApi/proto` restores the previous output.
3. `dotnet pack -c Debug -p:IncludeSymbols=true -p:SymbolPackageFormat=snupkg`. Package validation
   runs against `PackageValidationBaselineVersion`, and the pull request's `build` check runs it
   too. If it fails because the protocol
   removed or changed public API, rerun with `-p:GenerateCompatibilitySuppressionFile=true` to
   create `LivekitApi/CompatibilitySuppressions.xml`, commit it, and describe every suppressed
   change in the changelog under "Breaking changes coming from livekit/protocol". Do **not** bump
   `PackageValidationBaselineVersion` or delete the suppressions file yourself: after the release
   is published, `publish.yml` opens a pull request that does both.
4. Diff the generated `Twirp.cs` for new RPCs or services and add the matching client methods,
   tests, README section and changelog bullets (and a sidebar entry for a new client). Then build
   and check the API reference (see that section).

`.github/workflows/sync-protocol.yml` does all of this unattended: it checks daily for a GA release
newer than the submodule, runs `/sync-protocol` with Claude Code, and opens a pull request from
`sync-protocol/vX.Y.Z` with three commits: `Update livekit/protocol to vX.Y.Z` (the submodule),
`Regenerate proto C# files` (`generate_proto.sh` and `LivekitApi/proto`) and
`Adapt LivekitApi to livekit/protocol vX.Y.Z` (everything else). Its header lists the secrets and
repository settings it needs. A version whose branch exists is skipped; deleting the branch retries it.

## Upgrading rust-sdks (RTC SDK)

1. `cd LivekitRtc/rust-sdks && git fetch --all && git checkout livekit-ffi/vX.Y.Z && cd ../..`
2. `./generate_proto.sh`
3. `./LivekitRtc/download_ffi.sh livekit-ffi/vX.Y.Z` (all six binaries change).
4. `dotnet build`, then run at least the no-Docker RTC tests (the parity guards) and the Docker
   tests you can afford. Expose any new proto fields the guards complain about. Build and check
   the API reference too: a public member that starts using another `LiveKit.Proto` type needs it
   in the allow-list of `docs/filter.yml`.
5. `dotnet pack -c Debug -p:IncludeSymbols=true -p:SymbolPackageFormat=snupkg`. Package validation
   compares `LivekitRtc` with its `PackageValidationBaselineVersion` (the last RTC release), as for
   the API package. The generated `LiveKit.Proto` types are public, so an FFI proto that removes
   or changes a member breaks the package: rerun with
   `-p:GenerateCompatibilitySuppressionFile=true` to record it in
   `LivekitRtc/CompatibilitySuppressions.xml` and explain it in the changelog under
   `Breaking changes coming from rust-sdks`. Hand-written public API changes only when the FFI
   forces it, and is suppressed and explained the same way. `publish.yml` moves the baseline and
   deletes the file after the release, as for the API package.
6. Commit the submodule pointer, regenerated protos, binaries and any `generate_proto.sh` change
   together as `Update "rust-sdks" to livekit-ffi/vX.Y.Z`, then the SDK changes, suppressions
   file, tests, docs and changelog entry as `Adapt LivekitRtc to livekit-ffi/vX.Y.Z`.

`.github/workflows/sync-rust-sdks.yml` does all of this unattended: it checks daily for a GA
`livekit-ffi` release newer than the submodule whose six binaries are published, downloads them
itself (`settings.json` asks before `download_ffi.sh`, which an unattended run cannot answer), runs
`/sync-rust-sdks` with Claude Code and opens a pull request from `sync-rust-sdks/vX.Y.Z` with those
two commits. As with `sync-protocol.yml`, a version whose branch exists is skipped.

## Changelogs and releases

- Each package has its own `CHANGELOG.md` (`LivekitApi/`, `LivekitRtc/`), titled
  `# Changelog (Release Notes)`, newest first. It is embedded into the NuGet package as the release
  notes, so entries are user-facing: what changed for someone using the package, naming the public
  members involved in backticks, with links to README sections, PRs or issues. Internal refactors
  and test-only changes do not get entries.
- Bug-fix bullets state the user-visible symptom first (crash, dropped event, the exact log
  line), then the cause and the fix. The RTC changelog has examples.
- Unreleased work goes under a `## Unreleased` heading at the top. Add a bullet in the same
  change that introduces the behavior.
- A dependency bump is always the first bullet of its version, in this form (plus the commit or
  PR links described below):
  - `Update livekit/protocol to [vA.B.C](https://github.com/livekit/protocol/releases/tag/%40livekit%2Fprotocol%40A.B.C)`
  - `Update rust-sdks to [livekit-ffi/vA.B.C](https://github.com/livekit/rust-sdks/releases/tag/livekit-ffi%2FvA.B.C)`
- API changes forced by a protocol upgrade go under a nested `Breaking changes coming from
  livekit/protocol:` list, one bullet per affected client-facing member (a suppression for the
  generated `Twirp` counterpart folds into the same bullet). In the RTC changelog, those forced
  by a rust-sdks upgrade go under `Breaking changes coming from rust-sdks:` the same way.
- Every bullet ends with a link to the change that landed it: `[PR #N](<repo>/pull/N)` when there
  is one, otherwise `[commit <short sha>](<repo>/commit/<full sha>)`.
- The release commit is `Release X.Y.Z of <PackageId>`: it bumps `<Version>` in the csproj and
  renames `## Unreleased` to `## X.Y.Z` (releases before November 2026 added the heading
  directly). `<Version>` in each csproj is the only version source:
  `FfiClient.SdkVersion` reads it from the assembly's informational version at runtime, so
  never hard-code a version string in code.
- Publishing happens when the maintainer creates a GitHub release whose tag is `api-X.Y.Z` or
  `rtc-X.Y.Z` (the prefix selects the package). `publish.yml` packs, validates, tests, pushes to
  NuGet, then opens the pull request `Post steps release <tag>` (branch `post-release/<tag>`) that
  moves the package validation baseline. A ruleset on `main` requires the six checks of
  `dotnet.yml` (`build`, `RTC tests (linux-arm64)` and the four `RTC native tests (<rid>)`; a
  renamed job or matrix entry must be renamed in the ruleset too) and lets only repository admins
  bypass it (a personal-account repository cannot list GitHub Actions as a
  bypass actor), so workflows change `main` only through pull requests, and GitHub holds the
  checks of a pull request opened with `GITHUB_TOKEN` until the maintainer approves them. Merge
  that pull request before the next release of the same package. The push to NuGet uses NuGet Trusted
  Publishing (`NuGet/login` exchanges the job's OIDC token for a short-lived key): nuget.org holds
  a policy for this repository and workflow file scoped to the two package IDs, and the
  `NUGET_USER` repository secret holds the nuget.org user name. There is no long-lived API key. Agents do not create tags or releases
  and never run `dotnet nuget push`; `.claude/settings.json` denies `gh release` and
  `dotnet nuget push` and asks before `git tag`.
- Tags without a prefix (`1.0.2` ... `1.2.0`) are old API releases from before the RTC package existed.

## Agent tooling in `.claude/`

- `settings.json` pre-approves the routine commands (`dotnet build/test/pack/csharpier`,
  `./generate_proto.sh`, read-only `git -C <submodule> ...` for both submodules), asks before
  `git commit`, `git push`, `git tag` and `download_ffi.sh`, and denies `dotnet nuget push` and
  `gh release`.
- `hooks/guard-generated.sh` (PreToolUse) and `hooks/format-dotnet.sh` (PostToolUse) are
  described in the sections above. Both need `jq` or `python3`; the formatter needs
  `dotnet tool restore` to have run once.
- `/sync-protocol [version]` (`skills/sync-protocol/SKILL.md`) walks a livekit/protocol bump end
  to end: move the submodule, regenerate, fix the build, wrap new RPCs, detect breaking changes,
  write the changelog. It stops at a checkpoint before writing wrappers and never commits. Its
  two scripts are also useful on their own, run from the repo root:
  - `python3 .claude/skills/sync-protocol/scripts/proto_inventory.py`: protos listed in
    `generate_proto.sh` vs. the submodule, including imports that are not compiled.
  - `python3 .claude/skills/sync-protocol/scripts/api_coverage.py [--json]`: proto RPCs vs.
    generated Twirp routes vs. RPCs wrapped by a `*ServiceClient`. `scripts/coverage_ignore.txt`
    holds RPCs deliberately left out, with a reason (so far only commented-out candidates).
- `/sync-rust-sdks [version]` (`skills/sync-rust-sdks/SKILL.md`) is the RTC counterpart: move
  the `rust-sdks` submodule, regenerate the FFI protos, download the six matching binaries, fix
  the build, surface new FFI requests, events and option fields, detect breaking changes, run the
  parity guards and the e2e tests, write the changelog. Its `scripts/ffi_coverage.py [--json]` compares the
  `FfiRequest`, `FfiEvent` and `RoomEvent` oneofs with what the hand-written sources
  (`LivekitRtc/*.cs`, `LivekitRtc/Internal/*.cs`) actually send, read and handle; deliberate gaps
  go in `scripts/coverage_ignore.txt`.

## Git hygiene

- Commit subjects are short imperative sentences; recent RTC fixes use `fix(rtc): ...` (use
  `fix(api): ...` for the API package by analogy). Mechanical commits keep their fixed subjects (see the upgrade and release
  sections) so they are greppable in history.
- Never commit `bin/` or `obj/`.
- Package versions live only in `Directory.Packages.props` (central package management): every
  project, examples included, gets one version of each package, so both libraries always ship the
  same `Google.Protobuf`. A `PackageReference` never carries a `Version` (error NU1008); add a
  `PackageVersion` there instead. Tools run by scripts or workflows are pinned in
  `.config/dotnet-tools.json` and run through `dotnet tool restore`, never installed unpinned.
- Dependabot updates both files weekly from a single `nuget` entry, one pull request per dependency
  across all projects (`group-by: dependency-name`); the CSharpier tool and package, and the
  Testcontainers packages, come grouped.
- Workflows pin every action to a full commit SHA, never a tag or branch, with the release in a
  comment on the same line (`uses: actions/checkout@<40-char sha> # v4.4.0`). Dependabot's
  `github-actions` entry bumps both together. Pin a new action the same way: resolve the release
  tag with `git ls-remote --tags https://github.com/<owner>/<repo>`, using the `^{}` line of an
  annotated tag.
- Clone with `--recurse-submodules`; a plain `git submodule update --init --recursive` is enough to
  regenerate protos. Building the FFI from source additionally needs `--checkout` for the nested
  submodules (see the RTC README).
